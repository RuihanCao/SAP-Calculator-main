# exp01 W0 harness: record the real game animating an injected battle

This harness makes the real Super Auto Pets WebGL client animate a battle we
choose, and records that animation as a clip plus a filmstrip.
It is the ground-truth side of the fight-animation parity work.

## Where it runs

The browser runs on the AutoDL box (`ssh myAutodl`), not on the VPS.
The VPS has 1 CPU and 1.6 GB of RAM, and a Unity WebGL build under SwiftShader software rendering is unusable there: a single CDP screenshot took 26 to 36 seconds and the game never got past "Pinging servers".
The box has 32 cores and 377 GB of RAM, boots the game to the consent dialog in about 150 seconds, and screencasts at roughly 30 frames per second.

The box cannot reach `teamwood.itch.io`, but it can reach `html-classic.itch.zone` and `api.teamwood.games`, which is everything the game itself needs.
So the driver loads the Unity build directly instead of going through the itch.io wrapper page, and aborts requests to `static.itch.io` (unreachable from the box, and it stalls page load for about 100 seconds).

Resolve the build id from the outer page when it changes:

```
curl -s https://teamwood.itch.io/super-auto-pets | grep -o 'html-classic.itch.zone[^"\\]*'
```

Then set `ANIM01_GAME_URL` for `driver.py`.

## Layout

| file | what it does |
| --- | --- |
| `driver.py` | long-lived Playwright daemon: one persistent Chromium profile, one page, battle interception always armed, file-based command queue |
| `ctl.py` | client for the driver, one command per invocation |
| `build_payload.py` | fixture spec to real `/api/battle/get` battle payload |
| `sim_notes.js` | fork-sim determinism verdict plus the expected event sequence for a fixture |
| `sim_config.js` | fixture spec to fork `SimulationConfig` |
| `check_fixtures.sh` | runs `sim_notes.js` over every fixture, writes `expected/<id>.txt` |
| `run_fixture.py` | drives the game to the battle for one fixture and records it |
| `record_calc.py` | the mirror of `run_fixture.py` for our own app: loads a fixture through the share-state URL, plays the event driven animation and screencasts it |
| `controls_probe.py` | same entry, plus a timed script of replay-control presses, for the speed mode and the stop/skip/rewind grammar |
| `make_clip.py` | frame directory to webm clip plus filmstrip contact sheet |
| `crop_strip.py` | one screen region over a time window, upscaled, for reading a widget frame by frame |
| `fixtures/*.json` | the 16 fixture specs |
| `expected/*.txt` | fork-sim expected log sequence per fixture, regenerated by `check_fixtures.sh` |
| `expected/events/*.json` | golden structured animation event stream per fixture, W1, regenerated by the vitest specs |
| `data/battle-template.json` | battle payload template, from the extension's captured `battle_override.json` |
| `data/enum-maps.json` | pet, perk, toy and ability enum maps, extracted from the extension's generated `calculator_maps.js` |

Clips and payloads are written outside git, under `/root/autodl-tmp/sap-data/anim01/`.

## Structured animation events (W1)

The engine emits a typed `AnimationEvent[]` alongside the prose logs.
Dump one fixture's stream with the headless CLI:

```bash
node simulation/dist/cli.js simulate --dump-events -i <config.json> --pretty
```

The goldens under `expected/events/` are asserted by `tests/specs/animation/`.
Regenerate them deliberately, then read the diff against CHECKLIST.md before committing:

```bash
UPDATE_ANIMATION_GOLDENS=1 npx vitest run --config config/vitest.config.ts tests/specs/animation
```

## Recording our own animation (W2)

The calculator side of the comparison is recorded from the dev server on the box:

```bash
# dev server, box only, 127.0.0.1:4200
node ./node_modules/@angular/cli/bin/ng serve --proxy-config config/proxy.conf.js --host 127.0.0.1 --port 4200

export PLAYWRIGHT_BROWSERS_PATH=/root/autodl-tmp/ms-playwright
/root/workspace/.venv-sap/bin/python record_calc.py --all --seconds 60
for d in /root/autodl-tmp/sap-data/anim01/calc/f*; do
  /root/workspace/.venv-sap/bin/python make_clip.py "$d" \
    --out-dir /root/autodl-tmp/sap-data/anim01/calc/out --tiles 40 --mode even
done
```

The fixture boards are loaded through the app's own `?c=<json>` share state, so nothing in the app is special cased for the recording.
For the clip the stage element is reparented into a full viewport holder, which frames the animation the way the reference clips frame the real game; it is the same live component, only moved.
Clips and filmstrips land in `/root/autodl-tmp/sap-data/anim01/calc/`, alongside the real game's under `.../anim01/out/`.

## Interception: route fulfilment, not the page hook

`driver.py` uses Playwright `context.route("**/api/battle/get/*")` and fulfils the request itself.
The extension's `page_hook.js` fetch and XHR patches were the documented fallback if route fulfilment tripped CORS; that fallback was not needed.
Fulfilling the route with the request's own `Origin` echoed back in `access-control-allow-origin`, plus `access-control-allow-credentials: true` and an `OPTIONS` preflight reply, satisfies the client with no page-side patching at all.
As in `page_hook.js`, the requested uuid is copied onto the payload's `Id` before the reply, because the client matches the response id against the id it asked for.

## Getting to a battle

Two dead ends, recorded here so they are not retried:

- `History > Replays` shows "You have no replays" for a guest account, and the replay-code box does nothing for an arbitrary uuid.
- `History > Spectate` reports "You have no private versus games to spectate".

The working path is the arena.
Once per browser session, by hand:

1. Accept the privacy dialog, then `Play as Guest`.
2. `Play > Arena > Start`, answer `Play now!`.
3. `End turn`, `Confirm`, pick a team name, `Confirm`.
   The client posts `arena/ready` and then issues `GET /0.N/api/battle/get/{uuid}`, which the driver fulfils.
4. On the replay controls at the top of the battle screen, turn `AUTOPLAY` on so battles animate end to end instead of one clash per `PLAY` click.

After that the run sits on a post-battle shop screen, and `run_fixture.py` reuses that one battle slot for every fixture.
Leaving to the main menu and re-entering `Play > Arena` makes the client re-issue `GET /api/battle/get/{uuid}` for the same pending battle, and the driver answers with whatever payload is currently armed.
No arena progress and no extra turns are needed, so lives never run out.

## Rerunning

On the box:

```bash
export PLAYWRIGHT_BROWSERS_PATH=/root/autodl-tmp/ms-playwright
cd experiments/01-fight-animation-parity/harness

# 1. determinism check plus expected event sequences
./check_fixtures.sh

# 2. build one battle payload per fixture
/root/workspace/.venv-sap/bin/python build_payload.py --all -d /root/autodl-tmp/sap-data/anim01/payloads

# 3. start the browser daemon, wait for READY in the log (about 150 s)
nohup setsid /root/workspace/.venv-sap/bin/python driver.py \
  > /root/autodl-tmp/sap-data/anim01/work/daemon.log 2>&1 < /dev/null &

# 4. do the once-per-session arena setup above, by hand, using ctl.py
/root/workspace/.venv-sap/bin/python ctl.py shot --path /tmp/s.jpg
/root/workspace/.venv-sap/bin/python ctl.py click --x 640 --y 497

# 5. record every fixture
/root/workspace/.venv-sap/bin/python run_fixture.py --all

# 6. build clips and filmstrips
for d in /root/autodl-tmp/sap-data/anim01/clips/f*; do
  /root/workspace/.venv-sap/bin/python make_clip.py "$d" \
    --out-dir /root/autodl-tmp/sap-data/anim01/out --tiles 40
done
```

The python interpreter is `/root/workspace/.venv-sap/bin/python`, per the SAP venv convention.
Playwright and its Chromium live there and in `/root/autodl-tmp/ms-playwright`; Chromium had to be downloaded without `network_turbo`, because the turbo proxy MITMs TLS and the playwright downloader rejects its certificate.

## Driving the replay controls (W0b)

`controls_probe.py` enters a battle the same way `run_fixture.py` does, then fires a timed script of
control-bar presses and labelled screenshots at it, with the whole thing screencast.

```bash
# record a fixture with FAST engaged
controls_probe.py f04-summon-sheep fast-f04-summon-sheep "0.2=fast_on,0.8=park" --seconds=22

# pause at bar+2 s, look at it twice, resume at bar+8 s
controls_probe.py f04-summon-sheep ctl-pause \
  "0.2=fast_off,0.8=park,2.0=pause,2.6=park,4.0=shot,7.0=shot,8.0=pause,8.6=park,10.0=shot" --seconds=26
```

Two things it gets right that a naive timed script does not, both learned the hard way:

- Step times are measured from the moment the control bar is actually visible, not from the
  interception. The interception is found by polling and the bar fades in, so a press timed from the
  interception lands on a bar that is not clickable yet and is silently lost. Three probes were
  thrown away to that before the anchor was added.
- `FAST` is a toggle whose state survives between battles, so a blind press is a coin flip.
  `fast_on` / `fast_off` read the button out of the newest recorded frame and press only when the
  state is wrong. Engaged is drawn as a *dimmed* glyph; a hovered button draws a black focus ring
  that looks pressed and is not, which is why every probe parks the cursor with `park` before any
  screenshot.

Probe points, in the 960x600 screencast frame: the two white bars of the pause glyph at (415,60) and
(427,60) are both white only while the bar is on screen; the fast-forward glyph in (520,57)-(558,72)
peaks at 255 when FAST is off and at about 217 when it is on.

Control bar coordinates in the 1280x800 viewport: y=77, and x=483 rewind, 562 pause, 640 autoplay,
716 fast, 794 skip.

`REWIND` leaves the replay permanently stalled on this path; recovering the daemon needs
`ctl.py reload` plus about 150 s of boot, after which `Play > Arena` resumes the run.

## Reaching the victory and defeat screens

The client decides replay against new battle from the payload's `WatchedOn`.
With `WatchedOn` set the battle is a replay, top right reads `Replaying...`, there is no end screen,
and the pending battle is never consumed, which is what makes the one arena slot reusable forever.

`build_payload.py` grew three flags for the end screens:

```bash
build_payload.py fixtures/f01-plain-trades.json --unwatched --outcome 1 -o out/outro-victory.json
build_payload.py fixtures/f01-plain-trades.json --unwatched --outcome 2 --swap-boards -o out/outro-defeat.json
```

- `--unwatched` clears `WatchedOn`, so the client accepts the battle as real, shows the end screen,
  and consumes the turn.
- `--outcome` writes the client's result enum, 1 win 2 loss 3 draw, which is what the end screen
  reads. It is independent of who survives in the boards, so set it to agree with them.
- `--swap-boards` mirrors the fixture so the player side is the losing side.

Consuming the turn costs one life on a defeat, and afterwards the shop has to be ended again to get
a new pending battle. The recovery is: dismiss the end screen, close the guest tutorial popup, `End
turn` at (1148,714), `Confirm` at (827,415), and the run settles back on
`Looking for player opponent on the same turn...` with the slot reusable again.

## Guest tutorial popups

A guest account gets onboarding popups on the shop screen ("Buy a pet for 3 gold", "Get new pets in
the shop"). They are out of scope for parity and must not appear in cited frames. They close with
the orange X next to the bubble, and they only ever appear on the shop, never during a battle.

## Gotchas

- `page.screenshot` times out on the animating Unity canvas. Everything here uses CDP `Page.captureScreenshot` and `Page.startScreencast` instead.
- Unity renders continuously, so the screencast never goes idle. End of animation is detected by pixel stillness across recent frames, not by the frame stream stopping.
- The bundled Playwright ffmpeg is a minimal build: only the `pipe` and `file` protocols, so frames go in as `pipe:0`, and the input codec must be named with `-vcodec mjpeg` because this build cannot probe it.
- `node simulation/dist/cli.js --include-battles` throws `Converting circular structure to JSON`. `sim_notes.js` calls `runHeadlessSimulation(config, {includeBattles: true})` from `simulation/dist/index.js` instead.
- Board orientation: the fork's replay parser reads `Mins.Items` into `petArray[Poi.x]` and then reverses it, so `Poi.x = 4` is the FRONT pet on both boards. Verified on screen with f01: `Pig` at fixture index 0 renders front-most on the player side.
